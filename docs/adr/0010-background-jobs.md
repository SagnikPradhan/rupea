# Background work runs as jobs in Postgres

Slow work, like reading a statement with the table models, runs outside the request as a **job**: a name, a versioned payload of references (a ledger, a checksum, never file bytes), the user it runs as, a partition key and a dedupe key. Jobs of one name and partition key share a **partition**, and a partial unique index on running jobs, `jobs_name_partition_running`, lets one of them run at a time. The server claims the job due first whose partition runs none, locking it with `FOR UPDATE SKIP LOCKED`; it holds a lease it renews while a **worker** runs the job, and writes back whether it succeeded or failed. The jobs service owns the table and the workers; each service defines its own jobs as adapters over its application, so a job reaches the ledger through `withLedger` as its user, like a request does.

Delivery is at least once. A job may run again after a crash or a lost lease, so handlers are idempotent and check domain state first: a statement deleted while its job waited makes the job succeed doing nothing. A job runs one at a time per partition, and a job whose dedupe key is already waiting for the same user is not added again. One that is running does not count, since it may have read what changed since; when it fails, it makes way for the copy queued meanwhile instead of retrying. Both keys default when a job does not choose them: the partition to its user, the dedupe key to its payload. Partitions belong to a job's name, so jobs of different names never wait for each other. A job lists the errors worth retrying, `UnknownError` by default; it retries with exponential backoff and fails at once on any other error, which is kept for its user to see. A job whose worker stopped before finishing it backs off like an unknown error, so a job that crashes its process does not take down the next one at once. A job that runs longer than its timeout, five minutes by default, has its process killed and fails with `JobTimedOut`, which is not retried unless the job lists it; a hung run would otherwise hold its partition for good.

Enqueueing joins the caller's transaction. `atomically` opens one and provides it as `db`, so a statement and the job that reads it are written together or not at all, and nothing passes the transaction along.

Jobs run in **worker processes**. The server claims a job, holds its lease and records how it ended; a child process, from a tinypool pool, runs it. A raster or a model run then neither stalls requests nor, when native code crashes, takes the server down: a child that exits mid-job fails that job with an `UnknownError`, which retries like any other. Each worker builds its own context from the environment the server parsed and hands it, connecting to the same database, the server's embedded Postgres included. `src/worker.ts` is its entry, built by the same `vite build` as the server.

Rupee scales out, by running more replicas of one server against one database, so every replica claims jobs and concurrency is the normal case. `RUPEE_JOBS_WORKERS` says how many worker processes a replica runs at most, 1 by default, so a replica runs jobs as well as answering requests and the desktop app needs nothing else. Setting it to 0 stops jobs without losing them. `SKIP LOCKED` keeps claims off each other's jobs, the unique index keeps one job of a partition running, and leases hand back the jobs of a replica that died or was replaced mid-deploy. In the desktop app, with one worker, these look redundant; they are what lets the same code run as many replicas.

## Considered Options

- **A log, like Kafka, behind the port**: a log gives fan-out and replay, but no per-message retry, delay or status, and a message that keeps failing blocks its partition. Background work wants to be done once and retried alone. Partition keys keep the one thing a log does better, ordering per key.
- **pg-boss**: mature, with cron and throttling, but it owns its schema and connections, so queuing inside `atomically` needs an adapter over drizzle's transaction.
- **graphile-worker**: the same: it runs its own pool of connections and its own schema, which `atomically` would have to reach around.
- **Passing the transaction to `enqueue`**: every repository the caller writes through would need it too, which brings back threading `db`.
- **A `job_partitions` table that a claim locks, holding its running job and when its next one is due**: a claim reads one partition through an index, however long the backlog behind busy ones. But every path that ends or removes a job, a user's deletion included, has to keep that row in step, and claiming and ending a run each take several statements in a transaction. Benchmarked, it drained a queue at about half the rate.
- **A window function or a skip scan over the queued jobs, to find each partition's next one**: `FOR UPDATE` cannot lock a query with a window function, and both visit every partition with work on every claim: about five seconds a claim with a million partitions.
- **Running jobs in the server process**: simplest, but a long synchronous step stalls requests, and a crash in onnxruntime or pdfium takes the server with it.
- **Worker threads**: they keep requests responsive, but share the process, so a native crash still takes everything down.
- **Each worker process claiming its own jobs**: every process would hold leases and need its own supervisor. With the server claiming, the lease, retry and sweep code stays in one place and an off-the-shelf pool supervises the processes.

## Consequences

- The `jobs` table is the outbox. Another backend, when one is needed, still writes a row inside `atomically` and relays it; the row stays where a job's status is read. Who retries then, the broker or the table, is decided with that backend.
- `import-statement` is the first job: it files an uploaded ledger file for review. Its payload is the ledger and the checksum, partitioned by ledger so its rebooks never race and deduplicated on both, so uploading the same file twice queues it once. It does nothing when a file already cites the statement.
- A user sees their own jobs only. Nothing lists every job, since the service runs jobs for everyone.
- A server with free workers polls the table every second, as an outbox relay does, so nothing tells it a job was queued: a job is seen once its transaction commits, and the caller does nothing more. An idle claim matches no row and writes nothing, so polling costs well under a millisecond each time. `NOTIFY` would start jobs sooner, but holds a connection to listen on and never tells the server anything polling would miss.
- A claim reads queued jobs in `run_at` order past those whose partition runs one, so a backlog behind busy partitions slows every claim, by about half a millisecond per thousand such jobs on Postgres 18. A table holding each partition's next due time keeps claims constant, and comes back once backlogs reach hundreds of thousands of jobs.
- Two claims that pick jobs of one partition at once race on `jobs_name_partition_running`: the loser waits for the winner to commit, fails with `UniqueViolation`, and claims again past that partition. With 32 loops draining four partitions, about one claim in five lost, each costing about 0.3 ms.
- Finished jobs are deleted by the server: succeeded ones after a week, failed ones after a month. There are no scheduled jobs yet.
- A job's payload has a version. Changing a payload's shape bumps it. A server claims only the names it knows, at its version or older, so during a rolling deploy an old server leaves newer jobs to the new ones; an older version fails rather than being read wrongly. Within a partition, a server takes the next job it knows, so a newer one waits for a new server without holding up the rest. A job whose name no server knows fails with `JobUnknown` once it has waited a day.
- A worker that has run every model holds about 650 MB, its own copy of the models. Idle workers exit after five minutes, so an idle desktop holds none; the next job pays a second or two to start one.
- Only the server downloads models; workers check them, so a server claims jobs only once its models are downloaded, or failed to. Requests that still read statements themselves load the models in the server too, until that work moves into jobs.
- A dev reload kills the workers mid-job, and those jobs run again, each reload counting as an attempt. A production shutdown stops claiming and gives running jobs 20 seconds to finish, under the 30 that Kubernetes gives before killing the server; a job killed then is retried like any other whose process exited.
